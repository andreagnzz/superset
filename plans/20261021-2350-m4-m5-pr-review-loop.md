# Publish each finished plan issue as a pull request, loop fresh reviewers on it, and keep stacks rebased

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds.

Reference: This plan follows conventions from `AGENTS.md`, `packages/host-service/AGENTS.md`, `packages/trpc/AGENTS.md` and `.agents/commands/create-plan.md`. It covers milestones M4 and M5 of the roadmap `plans/20261021-1400-ade-perso-roadmap.md`.


## Purpose / Big Picture

After M2/M3 the host runs a plan's issues but stops at "the implementer says it is done". After this plan, the host also pushes each finished issue's branch, opens its pull request on the right base (the parent issue's branch for a stacked issue, the default branch otherwise), and starts a fresh Claude reviewer (no shared context, Opus at `high` from the `review` role of `routing.json`). The reviewer writes a verdict file; the host posts it as a PR comment, closes the reviewer, and either marks the issue done (approved) or sends the findings to the implementer, waits for its fix, pushes, and starts a new reviewer, up to three rounds. An issue still refused at round 3 is `blocked`, with its dependents. A stacked issue now starts only after its parent was approved.

To see it: `superset plan status <id> --local` shows `review` and the round, and each PR carries one "ADE review, round N: …" comment per round.

Stacks stay correct after the run: while a stacked pull request is open and its issue done, the host checks it at most once a minute. If its parent branch moved (someone pushed to the parent PR), it rebases the child's own commits onto the new parent head and force-pushes with a lease; if the parent PR was merged, it rebases the child onto the parent's base and points the child PR at that base. A child of a child follows in the same pass. A rebase that fails is aborted, commented on the PR, and that issue is left alone.

## Surprises & Discoveries

- Observation: an agent is "idle" for Superset as soon as its last hook event is anything but `Start` or a permission request, including the session start before the prompt is read. The first acceptance run treated a just-launched reviewer as finished, found no verdict, nudged it and replaced it every 15 to 25 seconds, and both issues ended "blocked: no valid review verdict" after three empty rounds. Implementers had escaped only because an empty transcript made the manager wait. The manager now acts only when the last hook event is `Stop` (`turnEnded`), or on the stale-state fallback.
  Evidence: host log of 2026-10-21 23:34–23:36 (review rounds 1–3 in under two minutes); `agentRunState` in `packages/shared/src/agent-status.ts`; test "waits for a reviewer's first turn to end, not for its first idle state".


## Decision Log

- Decision: the reviewer writes its verdict to `~/.superset/host/<org>/plan-runs/<run id>/<key>-round<N>.json`, outside the worktree.
  Rationale: a file inside the worktree could be committed by the implementer during a fix round; outside, it never touches the repository, and a fresh path per round means no stale verdict is ever read.
  Date/Author: 2026-10-21, Claude.

- Decision: publishing reuses the host's own procedures through internal callers: `git.push` (`gitPushTask` on a worker thread, publishes the branch under its own name) and `pullRequests.createForWorkspace` (base = the branch's configured base, which workspace creation set to the parent's branch for a stacked issue); comments go through `pullRequests.addComment`, reviewer cleanup through `terminal.killSession`.
  Rationale: no new git code on the host, no git on the main loop, and the same base rules the desktop uses.
  Date/Author: 2026-10-21, Claude.

- Decision: an issue is `done` only once approved, so its dependents start from reviewed code; implementers in a fix round and reviewers both count against the run's cap.
  Rationale: roadmap section 1 ("chacune relue par un reviewer à contexte neuf") and the cap's meaning ("agents actifs").
  Date/Author: 2026-10-21, Claude.

- Decision: after sending findings, the manager ignores the implementer's answers until a hook event newer than the message arrives (`askedAt`), as for the envelope nudge.
  Rationale: the implementer's previous `SUPERSET_WORKER_DONE` stays its last answer until it replies; reading it would publish an unfixed branch.
  Date/Author: 2026-10-21, Claude.

- Decision: a reviewer that ends its turn without a valid verdict is asked once to write it; if it still has none, the round is commented as "no valid verdict" and a new reviewer takes the next round, without disturbing the implementer.
  Rationale: there is nothing for the implementer to fix; the round still counts so a broken reviewer cannot loop forever.
  Date/Author: 2026-10-21, Claude.

- Decision: approval lives in the run file and in PR comments, not in a GitHub review.
  Rationale: roadmap D6: GitHub refuses that an account approves its own pull request.
  Date/Author: 2026-10-21, Claude.


- Decision: restack only issues that are `done` with an open pull request, at most once a minute per run, parents before children; also for runs already `done`.
  Rationale: a child in review or in a fix round has an agent in its worktree; once a run is done its stacks still need care until they are merged. Once a minute keeps GitHub calls low (`pulls.get` per published issue).
  Date/Author: 2026-10-21, Claude.

- Decision: record the branch's base commit (`merge-base` with its base) when it is first published, and restack with `git rebase --onto <new base> <recorded base>`; after a squash merge of the parent, onto the parent's base.
  Rationale: after a squash merge, the parent's commits are not on the base branch, so a plain rebase would replay them; the recorded base keeps only the child's own commits.
  Date/Author: 2026-10-21, Claude.

- Decision: the git work runs in two new worker tasks in their own module (`packages/host-service/src/workers/tasks/plan-stack.ts`), registered in `host-worker.ts`; `push --force-with-lease` only.
  Rationale: no git on the main loop; the lease refuses to overwrite a push someone else made to the child branch; a separate module keeps `tasks/git.ts` (upstream) untouched.
  Date/Author: 2026-10-21, Claude.
