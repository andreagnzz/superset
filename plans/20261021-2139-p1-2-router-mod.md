## Purpose / Big Picture

Claude Code starts "subagents" (child agents, through its `Agent` tool) to explore code, plan, or do a side task. By default a subagent runs on the model its caller picks, or on the parent's model, at the parent's effort. After this plan, every Claude Code session on the VPS `claude-vps`, including the ones Superset starts in workspaces, routes each subagent through one rules file, `routing.json`: an `Explore` subagent runs on Haiku at low effort, a `Plan` subagent on Opus at `xhigh`, a subagent whose task mentions "typo" or "rename" on Haiku, one whose task mentions "migration" or "security" on Opus at `xhigh`, and anything else keeps the parent's model. Editing `routing.json` changes the routing of the next subagent, with no restart.

To see it working: start `claude -p` on the VPS, ask it to call the Agent tool with `subagent_type: "Explore"`, and read the subagent's transcript: `requestedModel` is a Haiku id and `effort` is `low`.

  Rationale: the working copy changes with every branch switch; a session must never load a half-edited mod. `CLAUDE_CODE_PLUGIN_DIRS` is read by every Claude Code process of the user, including the ones Superset starts in a PTY, and needs no plugin install command.
  Date/Author: 2026-10-21, Claude.

- Decision: read `routing.json` from the plugin folder on every routing decision, and route nothing when it is missing or invalid.
  Rationale: edits apply to the next subagent without a reload. A broken rules file must never block or crash a subagent; the hooks have no `.catch`, so a hook that throws is skipped and the subagent keeps the caller's choice.
  Date/Author: 2026-10-21, Claude.

- Decision: skip forked subagents (`fork: true` / `subagent_type: "fork"`) and resumed ones.
  Rationale: Claude Code ignores a model for a fork and pins a resumed agent's content; rewriting them changes nothing or is refused.
  Date/Author: 2026-10-21, Claude.

## Context and Orientation

A Claude Code "mod" is a plugin folder with `.claude-plugin/plugin.json` and a TypeScript hooks module named by `hooks/hooks.json`. The module exports `register(on)`; `on(event, matcher?, hook)` adds a hook `($, e, next)`, where `$` is the engine interface, `e` the event's input, and `next(e)` runs the rest of the chain and the engine's behaviour. A hook changes the outcome by calling `next` with a rewritten input.

Two events matter. `agent.spawn` fires when a subagent is about to start; `e.subagentType` is its type (`general-purpose`, `Explore`, `Plan`, a plugin's agent), `e.prompt` its task, `e.model` the model the caller asked for, `e.fork` and `e.resume` mark forks and resumes. Calling `next({ ...e, model: "haiku" })` makes it run on Haiku, even over the caller's `model` (spike result A1). `tool.call` with the matcher `{ tool: "Agent" }` fires when the Agent tool is called; the tool's arguments are flat on `e` (`e.subagent_type`, `e.prompt`, `e.effort`), and `next({ ...e, effort: "low" })` sets the subagent's effort (spike result B1). `agent.spawn` has no effort field, which is why effort goes through `tool.call`.

`$.plugin.root` is the absolute folder of the plugin; `$.fs.read(path)` reads a file as text.

`claude plugin test <folder>` runs the folder's `*.test.ts` files inside the engine; a test imports `test` and `expect` from `claude-code/testing`, gets `$` and an `on` whose hooks stand for the engine beneath the plugin, so `on("fs.read", () => ({ value: "…" }))` answers the plugin's `$.fs.read`. `claude plugin validate <folder>` checks the manifest and lists the hooks.

Nothing in the monorepo's apps or packages changes. `biome.json` lints every file outside its exclusions, so the new files follow the repo's Biome format (tabs, double quotes). Turbo's `test` and `typecheck` tasks run per package and do not see `ade/`.


## Plan of Work

Milestone 1 writes the mod. `ade/router/routing.json` holds the roadmap's default grid. `ade/router/hooks/route.ts` holds the pure logic: `parseRouting(text)` turns the file into a typed `Routing` or throws on a wrong shape (unknown effort, missing tier, regex that does not compile), and `routeSubagent(routing, { subagentType, prompt })` returns `{ model, effort, reason }` or `null`. The order is the roadmap's: the subagent type mapped in `subagents` to a role wins; else, for `rules-or-parent`, the first rule whose `match` (a case-insensitive regex) finds the prompt gives a tier; else `null`, which means "leave the caller's or parent's choice". `ade/router/hooks/register.ts` adds the two hooks: on `agent.spawn` (not a fork, not a resume) it reads the rules and calls `next({ ...e, model })` when there is a route; on `tool.call` for `Agent` (not a fork) it does the same with `effort`. `ade/router/router.test.ts` covers one case per role and per rule, the no-match case, a fork, and an invalid `routing.json`, through the real hooks.

Milestone 2 deploys it: `rsync` to `~/.local/share/ade/router`, add `CLAUDE_CODE_PLUGIN_DIRS` to the `env` block of `~/.claude/settings.json` with `jq`, then run three headless checks and read the subagents' transcripts.

Milestone 3 records the result in the roadmap's Progress and Decision Log, commits on `feat/ade-p1-2-router`, pushes, opens a draft PR, and moves this plan to `plans/done/`.


## Concrete Steps

From `/home/andrea/code/superset` on the VPS.

    git switch -c feat/ade-p1-2-router main
    claude plugin validate ade/router
    # Expected: "Validation passed", hooks agent.spawn and tool.call{tool=Agent}
    claude plugin test ade/router

    mkdir -p ~/.local/share/ade
    rsync -a --delete --exclude='*.test.ts' --exclude='.claude-plugin/types' ade/router/ ~/.local/share/ade/router/
    jq '.env.CLAUDE_CODE_PLUGIN_DIRS = "/home/andrea/.local/share/ade/router"' ~/.claude/settings.json > /tmp/s.json \
      && mv /tmp/s.json ~/.claude/settings.json

Check on real subagents, each in an empty folder (same method as the spike's `run.sh`, without `--plugin-dir`, so the deployed copy is what loads):

    d=$(mktemp -d) && cd "$d"

      'Call the Agent tool exactly once with subagent_type "Explore", run_in_background false, description "probe" and prompt "Reply with the single word OK.". Then reply DONE.' \
      | jq -r .session_id
    # then: jq -c 'select(.type=="assistant") | {requestedModel, effort}' ~/.claude/projects/*/<session_id>/subagents/*.jsonl | sort -u

Repeat with `subagent_type "general-purpose"` and prompt "Fix the typo in README.md: reply with the single word OK." (expected Haiku, `low`), and with prompt "Reply with the single word OK." (expected the parent's model, `claude-sonnet-*`, and its default effort).


## Validation and Acceptance

Accepted when `claude plugin test ade/router` passes, `claude plugin validate ade/router` passes, and the three transcript checks above print the expected model and effort. Rollback is one command: remove `CLAUDE_CODE_PLUGIN_DIRS` from the `env` block of `~/.claude/settings.json`; new sessions then start without the mod.


## Idempotence and Recovery

The `rsync` and the `jq` edit give the same result when run again. If a session misbehaves, remove the env key as above; nothing else on the machine changes. A broken `routing.json` routes nothing; it never blocks a subagent.

## Interfaces and Dependencies

No new dependency. Types come from the engine (`import type { Register } from "claude-code"`; tests import from `claude-code/testing`).

In `ade/router/hooks/route.ts`:

    export const EFFORTS = ["low", "medium", "high", "xhigh", "max"] as const;
    export type Effort = (typeof EFFORTS)[number];
    export type Tier = { model: string; effort: Effort };
    export type Routing = {
      tiers: Record<string, Tier>;
      roles: Record<string, Tier>;
      subagents: Record<string, string>;
      rules: { match: RegExp; tier: string }[];
    };
    export type Route = Tier & { reason: string };
    export function parseRouting(text: string): Routing;
    export function routeSubagent(routing: Routing, subagent: { subagentType: string; prompt: string }): Route | null;

`fallbackTier` and `escalation` stay in `routing.json` for the launch estimator (roadmap M1, P1.4) and are not parsed here: subagents do not use them, because a subagent with no matching rule keeps its parent's model.
